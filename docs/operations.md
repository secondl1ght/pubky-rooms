# Operations: capacity, limits, and what to do when they are hit

Everything here is one node (no clustering in v1). Costs scale **per room and per followed user, never per viewer**: a viewer is a LiveView process reading a shared in-memory room; a followed user is one fiftieth of an event-stream connection to their homeserver.

## Limits at a glance

| What | Default | Where | When hit | How you notice | How to raise |
|---|---|---|---|---|---|
| Concurrent viewers (per room or total) | none | machine size | slower fan-out, higher memory (~50–100 KB per LiveView) | LiveDashboard (dev) or the exporter: `vm.memory.total`, run queues, `pubky_rooms.capacity.rooms` | bigger Fly machine (vertical); clustering is a later milestone |
| Followed users per homeserver per node (members of open rooms + signed-in users, each once) | 5 000 = 100 stream connections × 50 users | `PUBKY_STREAM_POOL_SIZE` (default 100) | new streams wait, then fail and retry every 30 s; those users' *new* messages stop arriving live until a connection frees; nothing crashes | `Subscriptions.info/0` in a remote shell; room notice + member marker "live updates unavailable" (from `Subscriptions` status broadcasts); `pubky_rooms.capacity.streams` vs `pool_size`, `GET /healthz` (`streams`/`stream_pool`), and a log warning when the pool crosses 80 % (once per crossing, cleared below 70 %) | raise the variable, redeploy; each connection is one socket and a little memory |
| Concurrent regular requests per homeserver (reads, listings, writes) | 50 | `PUBKY_HTTP_POOL_SIZE` | requests queue; bootstraps slow down; timeouts surface as "unreachable" and are retried | slow room opens; `pubky_rooms.room.bootstrap.duration` | raise the variable; keep `fetch_concurrency` below it |
| Bootstrap work per room | list every member's messages once (≤ `bootstrap_per_member` 50 entries each) and reactions once (≤ `reactions_per_member` 1 000, no fetches), fetch the newest `bootstrap_messages` 100, `fetch_concurrency` 16; paging lists one more page per exhausted member and fetches `page_size` 50 per round | `config :pubky_rooms` | opening a huge room takes seconds | `pubky_rooms.room.bootstrap.duration` / `.members` / `.messages` | tune the three values; M6 adds the detached cache and incremental first paint |
| Live-subscribed members per room | 5 000 (creator first, then key order); members beyond it are **polled**: their folders are re-listed every `member_poll_ms` (60 s) while the room has viewers. A poll is exact: it pages (≤ 40 pages of `bootstrap_per_member`) until it meets a message already held, fetches every new one, and treats a message older than one interval that left the listed range (the member's newest page at least) as deleted; edits by polled members and deeper deletions wait for the next bootstrap. Nobody is dropped; polled members' events still arrive live if anyone on the node follows them (e.g. their own session) | `max_members_subscribed`, `member_poll_ms` | polled members' messages show up with up to a minute of delay; a very chatty polled member (> 2 000 messages per interval) loses older ones until the room re-bootstraps (logged) | room notice "over the live-subscription budget" + timer marker on the member | raise `max_members_subscribed` together with `PUBKY_STREAM_POOL_SIZE` |
| Mute lists cache | one row per signed-in user who opened a room (two small sets); loaded on first use (two listings, 5 s cap, then empty until retried), refreshed after `mutes_ttl_ms` (15 min) for Pubky App changes, Rooms changes applied from events at once; rows idle for 4 × TTL are swept | `mutes_ttl_ms` | a Pubky App mute takes up to the TTL to apply here | — | lower the TTL at the cost of more listings per room open |
| Profiles cache | one row per user seen recently (~300 B); refreshed after `profile_ttl_ms` (15 min, 1 min after a failed fetch); rows older than 4 × TTL are swept every 15 min | `profile_ttl_ms` | stale names/avatars for at most the TTL | — | lower the TTL for fresher names at the cost of more `profile.json` reads |
| Presence / typing / viewer counts | in memory only (Phoenix.Presence per room + app-wide, PubSub typing signals with 4 s expiry); one meta per open tab of a signed-in user; anonymous viewers are only *counted* (the room server's viewer total, announced at most once per `viewers_debounce_ms` 2 s on a per-room stats topic), never tracked | `viewers_debounce_ms` | — | — | — |
| Warm rooms without viewers | 200 | `max_idle_rooms`, `room_idle_timeout_ms` 30 min | past 200, idle rooms stop after 1 s instead of 30 min and re-bootstrap on the next visit | — | raise `max_idle_rooms` if memory allows (a warm room is a few hundred KB) |
| Rooms that exist / rooms with viewers | none | — | — | — | — |
| Sessions in memory | none (a few KB each; dropped 60 s after the last tab closes, 15 min if never attached) | `session_memory_ttl_ms` | — | — | — |
| Room directory (DETS + ETS) | grows with rooms, memberships and tags known (~200 B each); Nexus tag counts in memory only | `PUBKY_DATA_DIR` | DETS files are limited to 2 GB | disk usage | fine to millions of rows |
| Closed rooms (read-only archives) | kept in the directory with `closed_at` and their members; forgotten by an hourly sweep when nothing touched them for `closed_room_ttl_ms` (90 days; opening the archive counts) | `closed_room_ttl_ms` | a former member no longer finds the archive in the lobby; messages stay on the authors' homeservers regardless | — | raise the TTL; `Directory.sweep_closed/1` runs it by hand |
| Nexus (mainnet discovery, optional) | two anonymous `GET /v0/stream/resources` calls every `nexus_sync_ms` (5 min) plus one `by-uri` lookup per room opened, at most every 5 min per room; nothing without `NEXUS_URL` | `NEXUS_URL`, `nexus_sync_ms` | discovery falls back to what this node saw itself; rooms keep working | lobby lists fewer rooms | check Nexus health; raise `nexus_sync_ms` if Nexus rate-limits us |
| Per-session write limits (protect homeservers and us) | messages (send/edit) 5 / 5 s, reactions 20 / 10 s, rooms 5 / h, room updates 20 / h, joins 20 / h, bans and unbans 20 / h, mutes and unmutes 20 / h, tags 20 / h (≤ 10 own labels per room), nickname 10 / 10 min; "retry" for unreachable members: signed-in viewers only, 3 / 10 s per viewer (one retry in flight per room); sign-in starts 20 / min per client (keyed by an HMAC of the client address — behind Fly the second-to-last `x-forwarded-for` entry, since Fly appends its own address last and Phoenix exposes only `x-` headers to LiveViews; else the peer — held in memory for at most two minutes, never logged or stored) | `PubkyRooms.Rooms`, `AuthLive` | user sees "Slow down — try again in N s" | — | code constants; make config if needed |
| Homeserver responses we accept | bodies up to `max_body` (library default 1 MiB for listings; Rooms reads files with 64 KiB, every reader validates at 16 KiB), each exchange bounded by a deadline of 3 × `request_timeout` (30 s) even while bytes trickle in; SSE lines and frames up to 64 KiB; on mainnet only public hostnames as endpoints (loopback, private, link-local addresses and `localhost`/`*.internal`/… are skipped) | `Pubky.Config` `max_body`, `allow_private_hosts`, `Pubky.Events.SSE.max_bytes/0` | the read fails as `:too_large` / `:unreachable` and the file or member is treated like any unreadable one | `pubky_rooms.fetch` errors | raise `max_body` in the library config if a legitimate file type grows past it |
| Live subscription retries | a member whose stream cannot be attached is retried after 30 s × (1…5 by consecutive failures) + up to 25 % jitter; stream calls guard against a stream that just died; a restarted `Subscriptions` stops every stream and broadcasts `:subscriptions_reset` (room servers acquire again; a signed-in user's own subscription returns on the next page load) | `subscription_retry_ms` | "live updates unavailable" notice per member until it succeeds | `pubky_rooms.stream.unavailable` | — |
| Room attach while bootstrapping | 5 s (`attach_timeout_ms`), then the page keeps its loading state and the `:ready` broadcast attaches it | `attach_timeout_ms` | a slow member homeserver delays the first paint of a cold room, never crashes it | slow room opens | — |
| Homeserver anonymous read throttle | operator-set, e.g. 1 MB/s per IP | homeserver `[default_quotas] unauthenticated_ip_rate_read` | our reads slow down (delay, not error) | slow bootstraps only | ask the operator to whitelist our IP for count limits; `PUBKY_SERVICE_CREDENTIAL` for authenticated reads with an unlimited quota (deferred to after launch) |
| Homeserver request-count limits | operator-set per path (`429` + `Retry-After`) | homeserver `[[drive.rate_limits]]` | we back off and retry once; history of the affected member shows as unreachable with Retry | room banner | operator whitelist |

## Deploy targets

| | Staging | Production |
|---|---|---|
| Fly app / host / region | `pubky-rooms-staging` → `pubky-rooms-staging.fly.dev` (placeholder), `fra` (next to the staging stack in Zürich) | `pubky-rooms` → `rooms.pubky.app` (custom domain, later), region next to the mainnet homeserver |
| `PUBKY_NETWORK` | `staging` (public PKARR relays + `httprelay.staging.pubky.app` + `nexus.staging.pubky.app` + the sign-in page's Pubky App link → `https://staging.pubky.app`, password-protected; identities from Pubky App staging live on `homeserver.staging.pubky.app`) | `mainnet` (+ `NEXUS_URL=https://nexus.pubky.app`) |
| `PHX_HOST` | the Fly hostname | `rooms.pubky.app` |
| `PUBKY_DATA_DIR` | `/data` (a Fly volume; the room directory DETS) | same, its own volume |
| Secrets | `SECRET_KEY_BASE` only (`mix phx.gen.secret`) | same, its own value |
| Optional | `PUBKY_APP_URL` (the "New to Pubky?" link; default `https://pubky.app`), `PUBKY_CLIENT_ID` (defaults to `PHX_HOST`, what Ring shows) | same |

Staging and production are separate Fly apps: no shared volume, secrets or sessions. Every `PUBKY_*`/`NEXUS_*` variable overrides its preset value individually.

## Deploy steps (Fly)

The release is standard Phoenix (`mix phx.gen.release --docker`, Elixir 1.18.3 / OTP 27.3.4.6 on Debian trixie). The `Dockerfile`, `.dockerignore` and `fly.toml` sit at the **repository root** because the app depends on the sibling library by path (`{:pubky, path: "../pubky_ex"}`): the build context is the whole repo and the Dockerfile copies `pubky_ex/` and `pubky_rooms/` into the builder. `pubky_rooms/rel/overlays/bin/server` starts the release with `PHX_SERVER=true`. The runtime image runs as `nobody`, listens on `PORT` (8080 on Fly) and keeps the DETS directory under `PUBKY_DATA_DIR` (a volume at `/data`; the image creates the directory owned by `nobody`).

Check the image locally before touching Fly (a container has its own `/data`, so this is safe next to a running dev server):

```bash
docker build -t pubky-rooms:staging .
docker run --rm -p 127.0.0.1:8080:8080 -e SECRET_KEY_BASE="$(cd pubky_rooms && mix phx.gen.secret)" \
  -e PHX_HOST=localhost -e PORT=8080 -e PUBKY_NETWORK=staging -e PUBKY_DATA_DIR=/data \
  -v pubky-rooms-local-data:/data pubky-rooms:staging
curl -s http://localhost:8080/healthz      # 200 {"status":"ok",…}; /login shows the staging Pubky App link
```

`PHX_HOST=localhost` keeps the HTTPS redirect out of the way (`force_ssl` excludes that host); the share image, fonts and `sw.js` are served from their digested paths; the service worker registers in a real browser (headless Chromium is fine, the in-app browser pane refuses workers). Remove the container and the `pubky-rooms-local-data` volume afterwards.

First deploy of the staging app (each command creates or changes something on Fly; `fly.toml` at the root carries the app name, region, env, volume mount, health check and VM size):

```bash
fly apps create pubky-rooms-staging --org personal
fly volumes create pubky_rooms_data --app pubky-rooms-staging --region fra --size 1 --yes
fly secrets set SECRET_KEY_BASE="$(cd pubky_rooms && mix phx.gen.secret)" --app pubky-rooms-staging
fly deploy --app pubky-rooms-staging --ha=false --local-only
```

Region `fra` (Frankfurt): the whole Pubky staging stack (homeserver, Nexus, HTTP relay, both PKARR relays) runs on Google Cloud in Zürich (`34.65.0.0/16`, europe-west6), and every write confirmation and every live event goes app ↔ homeserver, so the app sits next to it (about 10 ms) while browsers anywhere pay one websocket hop; from the US west that is about 140 ms, which LiveView absorbs (typing is local, sends confirm on the next round trip). VM `shared-cpu-2x` with 1 GB: the second vCPU covers a bootstrap burst (concurrent fetches, JSON, rendering for every viewer of the room) and the memory is headroom for many warm rooms; under $10 a month, changed with `[[vm]]` in `fly.toml` and a redeploy. What actually bounds speed is the homeserver round trip and its anonymous read throttle, not the VM.

`--ha=false` keeps one machine (one volume, one DETS file; a second machine would need its own volume and would run a second, independent directory). `--local-only` builds with the local Docker and pushes the image; drop it to use Fly's remote builder. The secret is generated straight into the command and never printed or stored. Later deploys are `fly deploy --ha=false --local-only` from the root; a redeploy replaces the machine in place, the volume stays attached, sessions survive through the cookie.

Fly's init mounts the volume owned by the image's user (`uid 65534`, `nobody`), so no chown step is needed; the log shows `Mounting /dev/vdc at /data w/ uid: 65534`. Expect one health-check failure line in the two seconds before the endpoint listens (inside the grace period) and, from a sandboxed shell, a harmless flyctl DNS-check timeout after the deploy.

After the deploy: `fly status`, `fly checks list`, `fly logs` (no public keys, IPs or content at info), `curl -s https://pubky-rooms-staging.fly.dev/healthz`, then the smoke items of `docs/qa/checklist.md` §13 with the real Ring APK and a staging Pubky App identity. `fly ssh console` and `fly machine restart` are the two operator tools; `/app/bin/pubky_rooms remote` (the `console_command`) opens an IEx shell on the running node.

Learned on staging (2026-09-30): a **Fly trial account stops a machine after 5 minutes of running** ("Trial machine stopping" in the logs; the next request starts it again in ~3 s) — add a card before anyone relies on the deploy. Raising a live node to `:debug` (`Logger.configure/1` over `rpc`) is safe for the session since 2026-09-30 (LiveView's per-view logging is off, so the decrypted session with the credential is never printed; a test pins it) but still prints truncated public keys and request paths, so put it back to `:info` when done. The homeserver throttles the event-stream *connect* from Fly's address during a cold bootstrap (429, `Retry-After: 1`); the stream retries after the delay and `Subscriptions` logs "throttled by the homeserver (429), retrying in N ms" — a few per day is normal, a steady stream of them means the address is over a limit. To evaluate code on the running node without quoting trouble: `fly ssh console --command "/app/bin/pubky_rooms rpc 'Code.eval_string(Base.decode64!(\"<base64 of the code>\"))'"` (IO output comes back to the terminal).

**Deploys from GitHub (since 2026-09-30).** `.github/workflows/deploy.yml` runs when a CI run on `main` completes green (docs-only pushes skip CI, so they never deploy) or by hand (`gh workflow run "Deploy staging"`): it checks out the commit CI tested, `flyctl deploy --app pubky-rooms-staging --ha=false --local-only` on the runner's Docker with the repository secret `FLY_API_TOKEN` (a *deploy* token scoped to the staging app, created 2026-09-30 with `fly tokens create deploy -a pubky-rooms-staging -x 8760h`, so it **expires 2027-09-30**: create a new one the same way and `gh secret set FLY_API_TOKEN`), waits for `/healthz`, then runs `pubky_rooms/scripts/deploy_smoke.js` against the live app (~15 s). One deploy at a time (`concurrency`), never cancelled half-way. The smoke needs the two staging identities' Rooms session cookies as repository secrets (`STAGING_SMOKE_ALICE_COOKIE`, `STAGING_SMOKE_BOB_COOKIE`, the `_pubky_rooms_key` values of the harness profiles, stored 2026-09-30 by piping them into `gh secret set`, never printed) and the unlisted smoke room `/r/hckjqy…btky/0035SEP9WB4N2` ("Deploy smoke", alice owner, bob member; named in the workflow). When a cookie expires (30 days after its sign-in, so **around 2026-10-30**), the grant is revoked or `SECRET_KEY_BASE` changes, the smoke fails at "both identities signed in" — sign the profile in again (QR from the sign-in page) and store the new cookie. A red smoke means the app is deployed but something on the live path broke; fix forward or `fly releases` + `fly deploy` an older image. Deploying by hand with `fly deploy --ha=false --local-only` still works and is what the workflow does. Production gets its own job with its own token, secrets and smoke room when it exists.

Production later: a second Fly app (`pubky-rooms`) with its own `fly.production.toml` (`fly deploy --config fly.production.toml`), volume, secret and `PUBKY_NETWORK=mainnet` + `NEXUS_URL`; the custom domain `rooms.pubky.app` via `fly certs add` once DNS is ready.

## Runbook

Before every deploy: green CI (both projects + hook tests) and the **smoke** items of `docs/qa/checklist.md` on the testnet.

- **Rooms feel slow to open:** check the homeserver throttle first (is our IP whitelisted? are reads authenticated?), then `PUBKY_HTTP_POOL_SIZE` and `fetch_concurrency`.
- **Members' messages stop arriving live in many rooms at once:** stream pool exhausted or a homeserver rejecting streams. `Subscriptions.info/0` shows per-user status; raise `PUBKY_STREAM_POOL_SIZE` or check the homeserver.
- **Memory climbing:** count viewers and warm rooms (LiveDashboard); lower `max_idle_rooms` or move to a bigger machine.
- **Deploy / restart:** safe at any time. Sessions survive via the cookie; rooms re-bootstrap lazily on first open; the directory reloads from DETS. Expect a burst of homeserver reads as popular rooms reopen.
- **Homeserver down:** rooms whose creator's homeserver is unreachable show an error state; other rooms are unaffected. Members on a down homeserver are marked unreachable and retried every minute.
- **Stale assets after a deploy:** the service worker caches digested asset URLs only, so new deploys are picked up by the next page load; if a change to `sw.js` itself must reach installed apps immediately, bump its `VERSION` (old caches are deleted on activation).
- **`/healthz` returns 503:** the body names the missing process; the supervisor restarts it, so a persistent 503 means a crash loop — read the logs for that process and restart the machine if it does not recover.

## Telemetry and health (ADR 0006: aggregates only)

Every event comes from one module, `PubkyRooms.Telemetry` (its moduledoc is the contract): `pubky_rooms.stream.{connected,disconnected,unavailable}` counters (tag `reason`, a bounded atom), `pubky_rooms.room.bootstrap` (`duration`, `members`, `messages`; tag `status`), `pubky_rooms.message.confirm.duration` (send→confirm, tag `via` = `event` | `verify`), `pubky_rooms.message.lag.duration` (now − `created_at` of a message that arrived through a live event), and the 10-second `pubky_rooms.capacity` gauges (`streams`, `users`, `pool_size`, `rooms`, `directory_rooms`, `directory_members`) from the poller in `PubkyRoomsWeb.Telemetry`. Metric tags never carry keys, ids, IPs or content. Consumers: LiveDashboard at `/dev/dashboard` in dev; production has no exporter yet (add PromEx bound to a private interface when needed). The poller warns once when live stream connections reach 80 % of `PUBKY_STREAM_POOL_SIZE` and logs again when they fall under 70 %.

Browser hardening: every HTML response carries a strict Content Security Policy (`PubkyRoomsWeb.Plugs.SecurityHeaders`: scripts and connections only from this host, images from any `https:` host because avatars live on homeservers, no framing). Set `csp_img_src` (e.g. `["http:"]`) when a deployment must show images from plain-HTTP homeservers; a CSP violation shows up in the browser console, never as a server error.

`GET /healthz` (no session, no cookie) answers `200 {"status":"ok","streams":n,"stream_pool":size,"rooms":n}` while every core process (subscriptions, cursors, directory, mutes, profiles, sessions, rate limiter) is running, and `503 {"status":"degraded","missing":[…]}` otherwise. Fly checks point at it.
