## Bugs
- The "Connection lost" / "Something went wrong" toasts stacked icon, title, message and close button vertically (2026-09-28): they are revealed with `JS.show`, which writes an inline `display: block` over the toast's flex row (the same trap as the dialogs earlier). `Transitions.show/2` now takes `display:` and the layout passes `"flex"`. The reaction palette had it too (`JS.toggle`, emoji stacked in a column, 2026-09-28). Every `JS.show`/`JS.toggle` in `lib/` now states its `display:` explicitly and `js_commands_test` scans the source for any that does not. Gotcha: every `JS.show`/`JS.toggle` on a non-block element needs `display:`. — fixed
- Tag chips vanished when two adds were in flight (2026-09-28; e.g. a 400 ms round trip and Enter twice within 150 ms): a hook's `pushEvent` locks the hook element until its reply, a second push renews the lock, so LiveView patched a clone of the locked container for the first reply, and the second reply's `data-phx-skip` placeholders for the unchanged chips found no node to keep (empty spans). The hidden field still carried every label, so rooms were created correctly. Fix: the `TagInput` hook sits on the "+"/field control, so the chips and the hidden field are patched outside any lock. The same risk applies to any hook whose element contains server-rendered function components that change while its pushes are in flight (Composer: `typing`; ScrollToBottom: `load_older`) — check during the regression pass. The hooks had no tests at all (an omission from the plan, not a decision): vitest + jsdom now cover all five (`assets/test/hooks`), including the read-only limit state and the "hook element holds no chips" guard; the LiveView lock race itself still needs a real client. — fixed
- Hard refresh of a room page flashed placeholders ("Room" title, 0 members, no settings gear, a Join button for a member) before the real values: the disconnected first render used the mount defaults and only the connected mount asked the room server. The first render now takes the running room server's snapshot when the room is warm (any refresh: messages, anonymous count and the tag "+" included, nothing left to flash), paints a cold room from what the Directory knows (definition, members, tags, who is online, the viewer's own membership) with "Loading messages…" in the list, and a room this node has never seen gets one page-level loading state instead of placeholders (`scripts/headless_room.exs` makes one). Mute lists are cached or loaded (1 s cap) before any message is painted, and on a timeout the messages wait for the socket, so a muted author never shows and then vanishes. In that timeout fallback the members list also hides mute markers and mute/unmute actions (`mutes_known` assign) until the socket knows the lists, so nothing mute-related is ever painted wrong. Gotcha: whatever a LiveView needs for a flash-free first paint must be readable without the socket (ETS here), and `connected?/1` branches must fill it in. Dead-render test with `get/2`. — fixed
- The tag limit message flashed and disappeared: the hook disabled the focused input, disabling blurs, and the blur handler folded the field. The field is now read-only at the limit and stays open with the red placeholder until it is left; Backspace still removes the last chip. — fixed
- Every message rendered a blank line above its text and a stray indent (2026-09-28): the body `<p>` is `whitespace-pre-wrap` and the template's newline plus indentation inside it was rendered literally. The text now hugs its tags (`phx-no-format` keeps the formatter from reflowing it). Gotcha: any `pre`/`pre-wrap` element must open and close on the same line as its content in HEEx. — fixed
- Two hover buttons on messages rendered empty (2026-09-28): `lucide-smile-plus` and `lucide-trash-2` do not exist in the vendored Lucide set (1.45.0 renamed them; `history` was gone too), and a missing icon is silently no CSS. `icons_test` now scans every `lucide-*` name in `lib/` against `deps/lucide/icons`. — fixed
- Several message action pills could be open at once on phones (2026-09-28): the first fix wrapped toggle and pill in a `display: contents` element with `phx-click-away`, which LiveView skips because click-away only fires on elements with a box (`JS.isVisible` + `isInViewport`). ## Polish (found by Claude, signed-in pass)
- `/me` shows "No profile found yet" when the real problem is that the user's own key does not resolve (PKARR record gone; testnet relays lose them on recreation). Writes still succeed via the session, so a saved nickname never appears. Not distinguishable today: `Pubky.Storage.get` returns the resolver's `:not_found` unchanged, the same atom as a missing file, so the profile fetcher reads both as "no profile" (the stream layer sees the resolver error directly, hence rooms can flag it). Fix: wrap resolution failures in the library (`{:error, {:resolve, reason}}`), map to a distinct profile source in the cache, show "Your key does not resolve right now" on `/me`. ~1 h with tests. Low priority: on mainnet Ring republishes records. — open

## Staging deploy (2026-09-30)

**Result:** first deploy of `pubky-rooms-staging` (Fly, `fra`, `PUBKY_NETWORK=staging`) green on every check Claude can run alone (see the checklist run row); nothing to fix. Steps and reasoning in `docs/operations.md` "Deploy steps".

**Facts learned:**
- Fly no longer offers `den`; the Pubky staging stack (homeserver, Nexus, HTTP relay, both PKARR relays) is Google Cloud europe-west6 (Zürich), so the app went to `fra` — every write confirmation and live event is an app ↔ homeserver round trip, browsers pay one websocket hop.
- Fly's init mounts the volume owned by the image's user (`uid 65534` for `nobody`), so the standard Phoenix Dockerfile writes to `/data` without any chown trick; the image still creates `/data` for local runs.
- `x-forwarded-for` behind Fly's proxy is exactly `client, <Fly address>` (two IPv4 entries); the sign-in limiter's second-to-last rule is right.
- LiveView 1.2 turns its console debug log on for `localhost` hosts unless disabled; the staging hostname gets none.
- The in-app browser pane cannot register service workers ("unknown error fetching the script"); a real or headless Chromium does, so PWA checks use those.
- Phoenix serves static files before `Plug.Telemetry`, so a probe on `[:phoenix, :endpoint, :start]` never sees `/robots.txt`; use a routed path such as `/healthz`.
- Cosmetic: Fly logs one health-check failure line in the two seconds before the endpoint listens (inside the 15 s grace period, no routing effect); flyctl's post-deploy DNS check times out in a sandboxed shell (harmless).
