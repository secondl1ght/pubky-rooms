# QA

`checklist.md` is the manual pass itself: every flow, the expected result, which items need two identities, and the **smoke** subset to run before each deploy. It replaces ad-hoc regression passes and stands in for the browser end-to-end suite until one exists (post-launch backlog). Record each run in its table.

The finish phase ends with a **QA pause**: the user's first full manual run-through of the app on the testnet, plus Claude's regression pass, before the code-review and security-review skills run on the near-final repository and the first deployment happens.

What to record (decided 2026-09-22, to keep the file useful rather than complete): open or deferred items, decisions with their reason (so they are not re-argued), and bugs whose cause explains a gotcha. Trivial fixed items (a spacing tweak, a reworded hint) are not logged; the commit message is their record.

How to record: one line per finding in `findings.md` under the matching heading (`Bugs`, `Polish`, `Questions`), with the page/flow, what was expected, what happened, and how to reproduce. Claude works the list top-down, marks each row `fixed <commit>`, `deferred → <target>` (with the reason) or `not a bug` (with the explanation), and never deletes a row. Items that turn into design decisions move to the backlog table in `docs/PROGRESS.md`.

Every UI change is shown to the user as a screenshot (a real page when the state exists on the dev server, otherwise a fixture render, labelled as such) before it is reported done; the user judges the result, not the description of it.

Verification rule for fixes: tests and static renders prove markup and CSS; anything that only happens in LiveView's client (JS commands, hooks, click-away, focus, scrolling, dialogs) is verified in the in-app browser as the signed-in identity, at desktop and phone sizes, before it is reported done, and the report says what was checked where. The pane must be visible while probing: in a hidden pane LiveView's class commands wait on an animation frame that never fires (shim `requestAnimationFrame` with `setTimeout` from the JS tool if it cannot be shown).

Two-identity setup for manual testing: the in-app browser (Rooms + Ring Simulator tabs) and the connected Chrome hold separate cookies. Simulator identities vanish when its tab reloads, but Rooms sessions survive in the cookie; a fresh identity is one "Copy link" → Simulator Shortcut mode away.

## The regime (defined 2026-09-29, laid out 2026-09-30)
Every layer has its own job; none replaces another. The rule: the push gate never depends on a third party; checks against real services run at deploy time; what needs eyes or a phone stays manual.

| Layer | Checks | Runs | Status |
|---|---|---|---|
| Static gate | format, credo strict, warnings-as-errors, dialyzer | every push (CI) | done |
| Library suite | `pubky_ex` against an in-process fake homeserver speaking the real HTTP protocol | every push | done |
| App suite | rooms logic and LiveViews against `Pubky.Fake` and `FakeGrantLogin` | every push | done |
| Hook tests | the LiveView JS hooks (vitest + jsdom) | every push | done |
| Browser e2e | `pubky_rooms/test/e2e`: the checklist's **smoke** items in headless Chromium against the same fakes, the console collected (any error or warning fails, CSP violations included) | every push (CI job `e2e`) | done 2026-09-30 |
| Testnet integration | both projects' `:testnet` suites against the real homeserver and relays in Docker (writes, listings, sessions, events, restarts; sign-in through the library's own signer, no Simulator) | `main` pushes and before every deploy | to build |
| Deploy pipeline | build, deploy staging, production on approval (Fly's blue-green makes the new machine pass health checks first) | GitHub workflow with a Fly token | to build (today: `fly deploy` by hand, docs/operations.md) |
| Post-deploy smoke | against the deployed app: health and headers, the worker, Nexus tags of a listed room (read-only), and the two staging identities writing and seeing each other live in one **unlisted** smoke room (never in the directory, no tags, a stamped message deleted after the run), files checked on the homeserver | last step of the deploy workflow; never the push gate (shared services) | to build (the scratchpad harness is the prototype) |
| Visual regression | the key screens against baselines generated by CI's Chromium; a baseline-update workflow | every push, after the polish round | planned |
| Manual checklist (`checklist.md`) | visual judgement, the real Ring, the full pass | on staging: after the polish round and before production; the smoke subset after a batch of fixes | stays manual |
| Phone and Ring | install, the deep link, the installed window, iOS; revoke when Ring ships it | manual | stays manual |

Not part of the automation: the Ring Simulator (the library's signer covers the protocol; the Simulator stays a local manual tool) and a second e2e run against the testnet (browser + real homeserver is what the post-deploy smoke does; app + real homeserver is what the testnet job does).

Review findings (code-review / security-review) are triaged, never applied wholesale. Each one is assessed on its own: the regression risk of the fix, the severity and the consequences of leaving it, and how much re-verification the change needs afterwards. A critical bug is fixed before launch even when the fix is a refactor; a low-severity finding with a risky fix waits; a cheap safe fix for a minor finding can go in. Whatever is fixed gets re-verification scaled to the change (suites, smoke subset, the touched flow in the browser); whatever is not fixed becomes a tracked follow-up with the reason. Follow-ups live in `findings.md` and the backlog table until the plan is complete, then move to GitHub issues.
