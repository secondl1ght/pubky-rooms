# QA

`checklist.md` is the manual pass: every flow, the expected result, which items need two identities, and the **smoke** subset to run before each deploy. It complements the automated layers below rather than repeating them: what needs eyes, a phone or the real Ring stays manual.

## Recording findings
A finding is a bug, a polish item, a question or a decision. Bugs and polish items found by a run become GitHub issues, one per finding, with the page or flow, what was expected, what happened and how to reproduce; a fix that a checklist item should have caught adds that item in the same commit. Trivial fixes made on the spot (a spacing tweak, a reworded hint) are not logged; their commit message is the record. Decisions and their reasons go where they belong so they are not re-argued: an ADR for architecture, `docs/design-system.md` for the UI rules, `docs/operations.md` for limits. Maintainers may park follow-ups in `docs/maintainers/backlog.md` until they are triaged into issues.

## Verifying a fix
Tests and static renders prove markup and CSS. Anything that only happens in LiveView's client (JS commands, hooks, click-away, focus, scrolling, dialogs) is verified in a browser as a signed-in identity, at desktop and phone widths, before it is reported done, and the report says what was checked where. A UI change is shown as a screenshot rather than described: a real page when the state exists on the dev server, otherwise a fixture render labelled as such. Races in LiveView's own client (element locks, skip placeholders) are reproduced with `liveSocket.enableLatencySim(400)`. When the page is driven from an embedded browser pane, keep the pane visible: in a hidden one LiveView's class commands wait on an animation frame that never fires (shim `requestAnimationFrame` with `setTimeout` if it cannot be shown).

## Two identities
Two browsers, or two profiles, with separate cookies: identity A in one, B in the other, an anonymous viewer in a private window. With the Ring Simulator a fresh identity is one "Copy link" on `/login` and a paste into the Simulator's Shortcut mode; Simulator identities vanish when its tab reloads, but Rooms sessions survive in the cookie.

## The regime
Every layer has its own job; none replaces another. The rule: the push gate never depends on a third party; checks against real services run at deploy time; what needs eyes or a phone stays manual.

| Layer | Checks | Runs | Status |
|---|---|---|---|
| Static gate | format, credo strict, warnings-as-errors, dialyzer | every push (CI) | done |
| Library suite | `pubky_ex` against an in-process fake homeserver speaking the real HTTP protocol | every push | done |
| App suite | rooms logic and LiveViews against `Pubky.Fake` and `FakeGrantLogin` | every push | done |
| Hook tests | the LiveView JS hooks (vitest + jsdom) | every push | done |
| Browser e2e | `pubky_rooms/test/e2e`: the checklist's **smoke** items in headless Chromium against the same fakes, the console collected (any error or warning fails, CSP violations included) | every push (CI job `e2e`) | done 2026-09-30 |
| Testnet integration | both projects' `:testnet` suites against the real homeserver and relays in Docker (writes, listings, sessions, events, restarts; sign-in through the library's own signer, no Simulator) | every CI run (job `testnet`: the public `synonymsoft/homeserver-testnet` image, pinned, from `pubky/pubky-docker` at a pinned commit; nothing shared), so always before a deploy | done 2026-09-30 |
| Deploy pipeline | build, deploy staging, production on approval (Fly's blue-green makes the new machine pass health checks first) | `deploy.yml` after a green CI run on `main` (or by hand), a scoped Fly deploy token; production later | done 2026-09-30 (staging) |
| Post-deploy smoke | against the deployed app: health and headers, the worker, Nexus tags of a listed room (read-only), and the two staging identities writing and seeing each other live in one **unlisted** smoke room (never in the directory, no tags, a stamped message deleted after the run), files checked on the homeserver | last step of the deploy workflow (`pubky_rooms/scripts/deploy_smoke.js`, ~15 s, 14 checks; the cookies are repository secrets); never the push gate (shared services) | done 2026-09-30 |
| Visual regression | `pubky_rooms/test/vrt`: eight screens (lobby signed out and in, sign-in, the new-room dialog, a room with history, `/me`, lobby and room at phone width) against baselines generated by CI's Chromium (`**/__diff__/` holds the diff images); the "VRT baselines" workflow regenerates and commits them | every push (CI job `vrt`) | done 2026-09-30 |
| Manual checklist (`checklist.md`) | visual judgement, the real Ring, the full pass | on staging before a production deploy; the smoke subset after a batch of fixes | stays manual |
| Phone and Ring | install, the deep link, the installed window, iOS; revoke when Ring ships it | manual | stays manual |

Updating VRT baselines: after an intended visual change is pushed (its CI run goes red on `vrt`, as expected), `gh workflow run "VRT baselines" --ref <branch>` regenerates the PNGs with CI's Chromium, commits them to that branch and starts CI on the new head (`git pull` afterwards); on `main` that green run dispatches the deploy itself (a run started through `GITHUB_TOKEN` produces no `workflow_run` event, so CI's last job does it). The workflow pushes to a branch of this repository, so it cannot run for a pull request from a fork: a maintainer runs it on the branch after the change is in. A missing baseline makes the CI job fail rather than pass silently. Locally, `mix test --only vrt` compares against the committed baselines and writes `test/vrt/snapshots/__diff__/<screen>.png` on a mismatch; a local Chromium may render fonts a little differently, CI is the reference. What varies between runs is pinned or masked (message clock times are set to 12:00 in the page before the shot, the sign-in QR is masked) or seeded (three named identities, three rooms, one conversation); a few dozen pixels of tolerance cover the animated live dots.

Not part of the automation: the Ring Simulator (the library's signer covers the protocol; the Simulator stays a local manual tool) and a second e2e run against the testnet (browser + real homeserver is what the post-deploy smoke does; app + real homeserver is what the testnet job does).

Review findings (code-review / security-review) are triaged, never applied wholesale. Each one is assessed on its own: the regression risk of the fix, the severity and the consequences of leaving it, and how much re-verification the change needs afterwards. A critical bug is fixed before launch even when the fix is a refactor; a low-severity finding with a risky fix waits; a cheap safe fix for a minor finding can go in. Whatever is fixed gets re-verification scaled to the change (suites, smoke subset, the touched flow in the browser). Whatever is not fixed becomes a tracked follow-up with the reason: an issue, or a row in the maintainers' backlog until it is triaged.
